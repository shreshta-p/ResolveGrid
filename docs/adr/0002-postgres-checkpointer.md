# ADR 0002: LangGraph Checkpointer — AsyncPostgresSaver, and LLM Calls via Dependency Injection

## Status
Accepted

## Context
Phase 6 introduces the first LangGraph agent graph. Two implementation decisions needed to be made deliberately, not defaulted into: which checkpointer backs the graph's durability, and how graph nodes call the LLM given `services/agent-orchestration` is a workspace *library* `apps/api` (the app) depends on.

## Decision 1: `AsyncPostgresSaver`, not `MemorySaver`
LangGraph ships an in-memory checkpointer (`MemorySaver`/`InMemorySaver`) alongside `AsyncPostgresSaver`. `MemorySaver` is trivially easy to wire up but does not survive a process restart — the whole point of Phase 6's stated durability requirement ("kill process mid-run, confirm resume from last checkpoint rather than restart") is that state outlives the process. `AsyncPostgresSaver` persists to the same Postgres instance every other domain table already lives in, entered as an async context manager for the app's lifetime inside `apps/api`'s FastAPI lifespan, with `checkpointer.setup()` creating its own tables (confirmed idempotent). `InMemorySaver` is still used in `services/agent-orchestration`'s own unit tests, where real persistence isn't what's being tested — that's a correct, narrower use, not an inconsistency.

**Windows-specific finding, not part of the original decision but discovered wiring it up:** `AsyncPostgresSaver` uses psycopg's async driver, which raises `psycopg.InterfaceError` unconditionally under Windows' default `ProactorEventLoop`. Fixed with `asyncio.set_event_loop_policy(asyncio.WindowsSelectorEventLoopPolicy())` at import time in `apps/api/src/resolvegrid_api/main.py` — this fixes `TestClient`-based tests (which is what this repo's suite depends on) but not a real `uvicorn --reload` dev-server process on Windows without `--loop none` (uvicorn's own loop factory bypasses the global policy); irrelevant in the real Linux container deployment. Documented inline in `main.py` rather than silently worked around.

## Decision 2: graph nodes call an injected `complete_fn`, not `llm_gateway` directly
`apps/api/src/resolvegrid_api/llm_gateway.py` lives in the app, not a shared package. `apps/api/pyproject.toml` depends on `resolvegrid-agent-orchestration` (the graph library) — so the graph library importing `resolvegrid_api.llm_gateway` back would be backwards (a library depending on the app that depends on it), and would also saddle a pure orchestration package with FastAPI/SQLAlchemy/alembic as transitive dependencies it doesn't need.

Every node in `services/agent-orchestration/src/resolvegrid_agent_orchestration/graph.py` is built by a factory function taking a plain injected callable, `CompleteFn = Callable[[str], str]` — prompt text in, completion text out. `apps/api`'s lifespan wires in `complete_fn = lambda prompt: llm_gateway.complete(prompt).text` when it calls `build_graph(checkpointer, complete_fn)`. `services/agent-orchestration` has zero dependency on `resolvegrid_api` and no knowledge of `CompletionResult` (tokens/latency/provider/fallback info) — it only needs response text. This also makes every node trivially unit-testable with a bare lambda/fake, with no need to mock `apps/api` internals from inside the library's own test suite.

**An alternative considered and rejected**: wrapping the LLM call in a LangChain `ChatModel` (`init_chat_model`, `with_structured_output()`, etc.), which would have been the more "idiomatic LangChain" way to get `classify_intent`'s structured output. Rejected because `llm_gateway.complete()` already has real, tested behavior this project depends on (Ollama `think:false` tuning, LiteLLM fallback-header capture, cost computation via `PricingVersion`) that would have to be rebuilt inside a LangChain wrapper for no benefit — LangGraph itself has no requirement to use LangChain's model abstractions; any plain callable is a valid node. `classify_intent` gets its structured output by prompting for JSON and validating with a small Pydantic model directly.

## Decision 3 (methodology, not architecture): the checkpoint-restore test proves cross-instance persistence, not a literal process kill
The approved plan's literal wording for this exit criterion is "kill process mid-run at a node boundary, confirm resume from last checkpoint rather than restart." `apps/api/tests/test_checkpoint_restore.py` instead builds one graph/checkpointer instance, runs it to completion, fully tears it down, then builds a completely separate second instance (no shared Python object, connection, or event loop) and proves it correctly reads back the same persisted state via its own `aget_state()` call. This is deliberate: a literal OS-level process kill is flaky to automate reliably (this project already hit real, documented pain with forceful process termination on Windows during Phase 1's smoke-test work), and the actual property LangGraph's checkpointing exists to guarantee — state surviving being read by a completely independent object graph, with only the database in common — is exactly what a real process restart depends on too. Proving it directly is stronger, not weaker, evidence than an indirect, flaky process-kill would have been.

## Consequences
- Real Postgres durability is available to any future graph immediately, not just Phase 6's own.
- `services/agent-orchestration` stays a genuinely reusable, independently-testable library as more nodes/subgraphs are added in later phases (retrieval, tool-calling, the ADK specialist).
- The Windows event-loop-policy fix is a real, documented local-dev caveat that doesn't apply in production; anyone adding a new local Windows entrypoint that uses `AsyncPostgresSaver` needs to either import `resolvegrid_api.main` (which carries the fix as an import-time side effect) or apply the same policy themselves.
