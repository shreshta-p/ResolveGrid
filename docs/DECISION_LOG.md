| 2026-08-23 | `apps/api` allows a hardcoded dev-only CORS origin list (`localhost:3000`/`3001`), unconditionally applied with no environment gating | The API had no CORS middleware at all, which blocked every browser-based request from `apps/web`'s Next.js dev server (preflight failure), including the required manual browser verification for Phase 3 Task 5. No settings/config abstraction exists yet in `apps/api` (only ad-hoc `os.environ.get` calls), so this follows the same inline-comment-as-documentation pattern as the `X-Debug-Employee-Id` shim above rather than introducing a new config system. `allow_credentials=False`, so the wildcard `allow_methods`/`allow_headers` carries no credential-leak risk. Must become a real, environment-driven origin allowlist before any non-local deployment. | `apps/api/src/resolvegrid_api/main.py` |
| 2026-08-23 | Ticket state machine centralized in `packages/contracts`, not duplicated per-consumer | `ALLOWED_TRANSITIONS` is the single source of truth `apps/api` enforces against and `apps/web` reads for its transition-button affordance. A hand-copied frontend table already drifted once during Task 6 (missing `in_progress`→`closed`) before being caught in review — concrete proof duplication was the wrong call, not just a theoretical risk. | `packages/contracts/src/resolvegrid_contracts/tickets.py` |
| 2026-08-23 | In-memory (not Redis-backed) rate limiting accepted for ticket creation | `apps/api` runs as a single process today (modular-monolith ADR, no horizontal scaling yet), so a per-process sliding window is sufficient without adding a Redis dependency before anything needs it. Known related gap: rate-limit keys are never evicted and the limit is trivially bypassed by an attacker sending a fresh `X-Debug-Employee-Id` per request (that header is unauthenticated). Not worth solving independently of the auth shim it depends on. Revisit trigger: `apps/api` running as more than one process, or real authentication landing (fix both together). | `apps/api/src/resolvegrid_api/rate_limit.py` |
| 2026-08-23 | Hash-chained audit log's lack of row locking under concurrent writers accepted for Phase 3's scope | `record_audit_event` reads the previous row and writes the new one in the caller's transaction with no explicit lock; concurrent writers could both read the same "last" row and compute conflicting chains. Acceptable for Phase 3's single-writer-at-a-time scope. Revisit trigger: real concurrent ticket-mutation load, via `SELECT ... FOR UPDATE` or a serializable isolation level. | `apps/api/src/resolvegrid_api/audit.py` |
| 2026-08-24 | `generate_org()`'s seed wipe now protects audit-referenced employees (and their department/location/team) instead of blanket-deleting the whole table | Previously documented as an accepted local-only limitation (repeated dev runs after real ticket activity would hit a `ForeignKeyViolation` deleting an employee still referenced by `audit_log.actor_id`, since the log is append-only by design). This stopped being a narrow edge case once Phase 3 Task 7's own mandated fresh-state verification sequence — run the full test suite, *then* seed — started hitting it on every single run, not just repeated ones, since `test_tickets_api.py`'s fixture always commits real audit-referenced employees during the test run that precedes seeding. Fixed by excluding audit-referenced employees (and the department/location/team rows they'd otherwise orphan) from the wipe, rather than reworking the append-only audit design. Narrow, not a general transitive-closure solver — see the comment in `seed.py` for what it deliberately does not handle (e.g. manager_id chains, since no protected employee here ever sets one). | `apps/api/src/resolvegrid_api/seed.py` |
| 2026-08-24 | Ticket-summary prompts include raw, unsanitized ticket subject/message text with no prompt-injection defense | The approved architecture plan's prompt-injection boundary (treating retrieved/tool content as untrusted) is explicitly scoped to Phase 8's RAG pipeline and its adversarial test suite, not this phase's first non-agentic call. Blast radius today is low: no tool-execution loop exists yet for injected text to hijack, and the analyst viewing the summary already has raw read access to the same ticket body — the residual risk is a misleading/manipulated summary shown to a human who can already see the source, not a system compromise. Revisit before any later phase wires ticket content into an agent/tool-calling loop, where the same unsanitized pattern would be a real boundary violation, not just cosmetic. | `apps/api/src/resolvegrid_api/routers/tickets.py` (`summarize_ticket`) |
| 2026-08-24 | `ModelCall` rows have no actor field; `summarize_ticket` doesn't call `record_audit_event` | Every mutation elsewhere in this router (`create_ticket`, `transition_ticket`) is audited; this read-only endpoint currently is not, breaking that convention. Accepted for now because it's read-only (no state change to attribute) and Ollama calls are free, so cost accountability doesn't yet matter. Revisit once Phase 5 adds paid providers behind the same gateway — at that point, knowing who triggered a billed call becomes a real accountability requirement, not just consistency for its own sake. | `apps/api/src/resolvegrid_api/routers/tickets.py` (`summarize_ticket`), `apps/api/src/resolvegrid_api/models/telemetry.py` |
| 2026-08-24 | Deferred standing up Langfuse (trace/eval/cost UI) and Prometheus/Grafana to a later phase, descoping Phase 4's originally-planned exit criteria | The approved plan's Phase 4 exit criteria called for a call "visible... in ResolveGrid's ModelCall table, Langfuse, and Grafana." Standing up Langfuse's own stack (ClickHouse + MinIO + web/worker services) and Prometheus+Grafana is a materially large, separable infra addition, and per the approved architecture's own design, Langfuse is explicitly "a secondary deep-debugging surface, never the sole source of truth" — the ResolveGrid-owned `ModelCall`/`PricingVersion` tables are. Phase 4's actual deliverable (a real, non-mocked cost/latency badge) only requires the owned schema. Revisit trigger: any later phase that specifically needs Langfuse's trace-debugging UI or Prometheus/Grafana's infra-metrics dashboards, not just more `ModelCall` volume. | `docs/superpowers/plans/2026-08-24-phase4-model-gateway.md` ("Scope decision") |
| 2026-08-24 | Ollama model choice: `qwen3:14b` (9.3GB, fits the 4080's 12GB VRAM at 100% GPU residency) | Matched the approved architecture plan's stated choice exactly; no fallback to a smaller model was needed. Its default "thinking" mode was found to cost ~60x more tokens/latency for a short non-reasoning task and is disabled per-call via `"think": false` — see `apps/api/src/resolvegrid_api/llm_gateway.py`'s docstring for the measured numbers. | `infra/litellm/config.yaml` |
| 2026-08-25 | `ModelCall.fallback_occurred`/`serving_model_group` (bool + string), not a `routing_reason`/`fallback_reason` free-text field, per the approved plan's Phase 5 wording | Empirically verified against real, live Anthropic/OpenAI calls: LiteLLM signals a fallback via response HEADERS only (`x-litellm-attempted-fallbacks` count, `x-litellm-model-group`), never the body, and the upstream failure's actual reason text is never available anywhere in a successful fallback response — LiteLLM swallows it internally after a successful retry. A text-reason column would have nothing genuine to store; the schema only captures what's actually observable (that/which a fallback occurred). Revisit trigger: a future need to see the specific upstream error would require a separate lookup against LiteLLM's own spend/log API by call-id, not a bigger response payload. | `apps/api/src/resolvegrid_api/models/telemetry.py`, `docs/superpowers/plans/2026-08-25-phase5-cloud-fallback.md` |
| 2026-08-25 | Deferred per-provider scoped virtual keys + budget enforcement (the approved plan's Phase 5 "Security" bullet) to a later phase | Both `cloud-primary` and `cloud-fallback` currently share the single `LITELLM_MASTER_KEY` for all proxy access — there is no per-provider spend cap or key isolation yet. Implementing this properly means generating and storing real per-provider virtual keys via LiteLLM's `/key/generate` API (backed by its own dedicated Postgres DB, already set up in Phase 5 Task 1) and wiring budget limits — a genuinely separate, non-trivial addition, not a quick config tweak, and out of proportion to this phase's actual exit criterion (proving fallback routing works). Real money is now at stake with real providers wired up (unlike Ollama), which makes this a live gap, not a hypothetical one — flagged here rather than silently skipped, matching the Langfuse deferral's precedent. This also sharpens the still-open `summarize_ticket` actor-tracking gap noted 2026-08-24: with real paid calls now flowing, knowing who triggered a billed request is a real accountability requirement, not just a consistency nice-to-have. Revisit trigger: before any non-local/shared deployment, or before spend volume makes a shared unmetered key a real risk. | `infra/litellm/config.yaml`, `infra/docker-compose.yml` |
| 2026-08-25 | `summarize_ticket`'s `gen_ai.system` span attribute and error-path `ModelCall.provider` remain hardcoded to `"ollama"`, not derived from `llm_gateway`'s new `_MODEL_GROUP_TO_PROVIDER` map | Not a live bug today: `summarize_ticket` has no way to request anything but `llm_gateway.DEFAULT_MODEL` (no endpoint/UI lets a caller choose `cloud-primary`), so `"ollama"` is currently accurate in both spots. Left alone rather than exposing new public API surface in `llm_gateway.py` to serve a caller (a cloud-model-aware ticket-summarize path) that doesn't exist yet — that would be premature coupling to an undecided future feature, not a real fix. Revisit trigger: whenever `summarize_ticket` (or any future caller) gains the ability to request a non-default model — at that point both the span attribute and the error-path `ModelCall` construction must derive from the requested model instead of a literal. | `apps/api/src/resolvegrid_api/routers/tickets.py` (`summarize_ticket`) |
| 2026-08-26 | Agent graph nodes call an injected `complete_fn: Callable[[str], str]`, never `llm_gateway` directly; `classify_intent` uses manual JSON-prompt + Pydantic validation, not a LangChain chat-model wrapper | Full reasoning in `docs/adr/0002-postgres-checkpointer.md` (Decision 2) — summarized: `services/agent-orchestration` is a library `apps/api` depends on, so importing `resolvegrid_api.llm_gateway` back into it would be backwards and would saddle a pure orchestration package with FastAPI/SQLAlchemy as transitive dependencies. Dependency injection keeps the graph fully unit-testable with a bare lambda, and reuses `llm_gateway`'s already-tested behavior (Ollama tuning, fallback capture, cost) instead of rebuilding it inside a LangChain wrapper. | `services/agent-orchestration/src/resolvegrid_agent_orchestration/graph.py`, `docs/adr/0002-postgres-checkpointer.md` |
| 2026-08-26 | Checkpoint-restore test proves cross-instance Postgres persistence, not a literal OS process kill | Full reasoning in `docs/adr/0002-postgres-checkpointer.md` (Decision 3) — summarized: a literal process kill is flaky to automate (this project already hit real pain with forceful process termination on Windows during Phase 1); the actual property under test — state surviving a completely independent object graph with only the database in common — is exactly what a real restart depends on too, and is provable directly and deterministically instead. | `apps/api/tests/test_checkpoint_restore.py`, `docs/adr/0002-postgres-checkpointer.md` |
| 2026-08-26 | `classify_intent`'s `risk_level` field has no real enforcement tied to it yet | Matches the approved plan's own "establish the pattern early" framing for stage 2 — this is a deliberate sequencing choice (the field/schema exists before anything gates on it), not an oversight. There is also no `data_scope_tags` field at all yet, since that's inherently retrieval-era (Phase 7+). Revisit trigger: any future stage that needs to route or restrict behavior based on classified risk. | `services/agent-orchestration/src/resolvegrid_agent_orchestration/graph.py` |
| 2026-08-26 | `get_principal`'s debug-header shim still doesn't validate the employee id actually exists, confirmed to cause an unhandled 500 (not a clean 4xx) when a bogus id is supplied to an endpoint that writes a row with a real FK to `employee.id` | Already flagged as accepted "inherited risk" during Phase 6 Task 3's own review for `tickets.py`'s endpoints; independently reproduced during Task 5's manual `/chat` verification via `curl` (a nonexistent employee id → real 500, not 401/403). A real user is very unlikely to hit this today (the debug header only exists for a real, already-known local employee id), but it's a genuine gap that must close before this codebase's temporary auth shim is ever replaced with anything real. Revisit trigger: the same auth-shim replacement already tracked in the 2026-08-21 `X-Debug-Employee-Id` decision row. | `apps/api/src/resolvegrid_api/deps.py` |
| 2026-08-27 | `services/retrieval`'s embedder calls Ollama's `/api/embed` directly, bypassing LiteLLM, unlike every chat completion in this codebase (`llm_gateway.py`, always via LiteLLM for Anthropic/OpenAI fallback + centralized cost/usage logging) | `infra/litellm/config.yaml` defines no embedding route today (only the three chat `model_name`s), so going through LiteLLM here would mean adding a new route, not reusing one. `nomic-embed-text` is the only embedding model this phase uses and has no cloud-fallback requirement, so LiteLLM's actual value-add (provider abstraction, fallback, budget) doesn't apply yet. `services/retrieval` is also a zero-runtime-dependency library by design (`services/retrieval/pyproject.toml`) that shouldn't gain a dependency on `apps/api`'s LiteLLM master-key/env-var conventions just to reach Ollama.
