**Observations, reported honestly (not rounded favorably):**

- Recall@5 and precision@5 are effectively perfect on this corpus: every answerable query's single hand-labeled relevant chunk was retrieved within the top-5, in every case. This is a small-corpus effect, not evidence of a generally excellent retriever -- 36 total chunks (as few as 4-9 per authz-scoped subset) means near-exact lexical/semantic matches are much easier to surface than they would be against a realistically-sized enterprise corpus. This baseline should not be read as "retrieval is solved"; it is a floor to catch regressions, not a ceiling to claim.
- The one case that did NOT rank its correct chunk #1 was "Does Kestrel VPN access grant a flat connection to the entire corporate network?" (relevant chunk: `Kestrel VPN Access Policy (v2)`, ordinal 4, the "Access Scope" section) -- it ranked #3 (RR=0.333, nDCG@5=0.5), the only sub-1.0 case in the whole set. Plausible cause: that section's text has less direct lexical overlap with the query's exact phrasing ("flat connection to the entire corporate network" appears near-verbatim in the source text, but the fused rank still slipped behind two other VPN-policy chunks) -- not investigated further, since Task 9 is scoped to measuring and recording, not tuning retrieval.
- The VPN v1/v2 supersession distractor design worked as intended: across all 3 cases where the superseded v1 policy is a plausible-but-wrong answer (password rotation/MFA, password reset process, client software), v2's current chunk always ranked ahead of v1's superseded chunk. `Document.status`/RRF ranking wasn't given any explicit "prefer active over superseded" boost -- this result comes purely from v2's chunk text being a better lexical/semantic match for how the queries were phrased (asking about "current"/"today" policy), not from any status-aware logic in `retrieval.py`. A query phrased more ambiguously (not signaling "current") might not show the same separation -- worth a future, larger eval once supersession-aware ranking is a real feature, not just an emergent property of this hand-picked query phrasing.
- The two adversarial authz cases (`people_ops` principal asking about VPN password rotation; `it_support` principal asking about VPN client software) correctly returned zero leaked chunks from the security-tagged VPN policies, at any rank in the raw (pre-fusion) search results -- consistent with `test_retrieval.py`'s existing adversarial leakage test, now also exercised through this task's own golden queries rather than only hand-constructed fixtures.
- Regression-guard thresholds in `apps/api/tests/test_eval_retrieval.py` were set a bit below these observed numbers (recall@5 >= 0.85, precision@5 >= 0.15, MRR >= 0.80, nDCG@5 >= 0.80), specifically to tolerate normal `nomic-embed-text` embedding-call nondeterminism across runs without being a tautological assertion. The leakage and distractor checks are hard (zero-tolerance) assertions, not threshold-based, since those are correctness properties this corpus is specifically designed to make checkable exactly.

| precision@5 | 0.2000 | 0.2000 | +0.0000 |
| MRR | 0.9524 | 0.9643 | +0.0119 |
| nDCG@5 | 0.9643 | 0.9736 | +0.0094 |
| Adversarial authz leakage (`must_not_appear` violated) | None (0/18) | None (0/18) | unchanged |

**Honest interpretation -- this is NOT a straightforward "reranking wins" result:**

- **recall@5/precision@5 showed zero movement, as expected and predicted before running anything.** Phase 7's baseline was already at these metrics' mechanical ceiling on this corpus (every answerable case has exactly 1 relevant chunk, and it was always retrieved within the top-5) -- there was no headroom for reranking to show improvement on these two metrics regardless of reranker quality. This is a real ceiling effect, not a failure to detect a real signal; reporting "no movement" here honestly, not manufacturing an improvement narrative where none exists.
- **MRR and nDCG@5 did move, and positively, for a real, identifiable reason**: reranking fixed the one case that did NOT rank its correct chunk #1 in the Phase 7 baseline -- "Does Kestrel VPN access grant a flat connection to the entire corporate network?" (relevant chunk: `Kestrel VPN Access Policy (v2)`, ordinal 4, the "Access Scope" section), which ranked #3 in the baseline (RR=0.333, nDCG@5=0.5) and ranked #1 after reranking (RR=1.0, nDCG@5=1.0). This is a genuine ranking-quality improvement from the cross-encoder correctly recognizing this section's relevance despite its weaker lexical overlap with the query's exact phrasing -- exactly the kind of case a semantic cross-encoder is expected to help with over RRF-fused lexical+vector alone.
- **Reranking also introduced a real, measured regression the baseline did not have**, and this is reported plainly rather than buried under the positive nDCG/MRR numbers above: of the 3 VPN v1/v2 supersession-distractor cases (designed specifically to test that stale content doesn't outrank current content), 2 stayed correctly ordered (password rotation/MFA: margin widened from +5 to +3, still correct; password reset: margin unchanged at +1, still correct), but the third -- "What VPN client software should I currently install for Kestrel remote access?" -- **flipped from correct to incorrect**: the deprecated `Kestrel VPN Access Policy (v1, deprecated)` chunk (which names the now-unsupported "KestrelConnect Classic" client) now outranks the current `Kestrel VPN Access Policy (v2)` chunk (margin went from +1 in the baseline to **-1** after reranking; `distractor_beats_best_relevant` flips `False` -> `True`). RR for this case dropped from 1.0 to 0.5 and nDCG@5 from 1.0 to 0.631 (both cases still counted correctly in the aggregate recall/precision above since the relevant chunk still appears somewhere in the top-5 -- only its *rank* got worse). **Root cause, confirmed by review** (read the actual scored chunk text, not just the metric delta): this is NOT simply the reranker lacking staleness information. v2's own "client software" chunk text *does* state the current-vs-legacy distinction in-context ("current major version... legacy... no longer supported"); v1's competing chunk is a neutral technical description naming an exact version string ("3.x") with no staleness language of its own (the document-level "this policy has been superseded" framing lives in a *separate* chunk, ordinal 0, that isn't the one being scored here). The cross-encoder had partial information available in-chunk and still favored v1 anyway, by a thin, non-robust margin (rerank scores 0.989385 vs 0.980007, both saturated near the top of the sigmoid range) -- a genuine cross-encoder limitation (over-weighting topical/lexical specificity over an in-context recency cue), not an information gap. Dedup does not touch this pair (confirmed directly) -- the flip is 100% attributable to `rerank()` itself.
- **Net assessment**: on this specific 8-document/36-chunk corpus, reranking is a measured wash-to-slight-improvement on the metrics that had headroom (MRR/nDCG), zero movement on the metrics that didn't (recall/precision, ceiling-bound), and a genuine new failure mode on the one class of case this corpus was specifically built to stress-test (stale-vs-current content ordering) -- worse on 1 of 3 distractor cases, unchanged-but-narrower or wider on the other 2. This is not a "reranking clearly helps" result, nor a "reranking clearly hurts" result; it is a mixed, corpus-scale-limited signal that should inform (not settle) the decision of whether/how to wire reranking into the live graph in a later task. **A concrete, ready-to-use mitigation already exists and is not hypothetical**: `Document.status` (`apps/api/src/resolvegrid_api/models/knowledge.py`) is a real, already-populated column -- `Kestrel VPN Access Policy (v1, deprecated)` is `status="superseded"` and v2 is `status="active"` in the live DB right now -- and is currently consulted by nothing in the rerank/dedup/context-budget pipeline. A status-aware boost or penalty (e.g. deprioritizing/filtering `status="superseded"` documents before or after reranking) should be seriously evaluated as part of Task 7's wiring design, not deferred as a "maybe later" footnote; whatever Task 7 decides, it must re-run this comparison (or an equivalent check) afterward to confirm the flip is actually fixed, not just re-run the reranker/dedup unit tests in isolation.
- Regression-guard assertions in `apps/api/tests/test_eval_retrieval.py::test_reranked_eval_path_runs_end_to_end_against_real_corpus_and_reranker` reuse the same headline-metric floors as the Phase 7 baseline test (recall@5 >= 0.85, precision@5 >= 0.15, MRR >= 0.80, nDCG@5 >= 0.80, zero-tolerance leakage) plus a bounded assertion pinning the then-observed distractor regression at "at most 1 of 3 flips" (superseded by Phase 8 Task 7 below, which tightens this to zero-tolerance after the fix).

## Phase 8 Task 7 — status-aware distractor fix, real re-measurement (`phase8_reranking_v2`)

Fixes the regression Task 6 found: `resolvegrid_retrieval.status_adjustment.apply_status_adjustment` (new, Part B of Task 7) deprioritizes any reranked candidate whose `Document.status == "superseded"` by subtracting a full-range penalty (`DEFAULT_SUPERSEDED_PENALTY = 1.0`) from its rerank score before dedup -- since `rerank()`'s output is a `[0, 1]` sigmoid probability, this guarantees any non-superseded candidate always sorts ahead of a superseded one, regardless of how thin the original cross-encoder margin was (the Task 6 flip's margin was only 0.009 -- a smaller/multiplicative penalty tuned to survive that specific gap would have been a fragile, case-specific fix). Wired into both the real production pipeline (`apps/api/src/resolvegrid_api/agent_retrieval.py`'s `retrieve_for_agent`, order: fuse -> rerank -> status-adjust -> dedup -> budget) and the eval harness (`eval_retrieval.py`'s `evaluate_case`, same order, so a flip in the harness would mean the live graph has the same bug).

**Real re-measured distractor numbers** (commit at time of this entry: Phase 8 Task 7, `git log` for the exact hash; same `BAAI/bge-reranker-base`/`markdown-v1`/`heading-aware-v1`/`nomic-embed-text` versions as Task 6, `dedup_threshold=0.30`, `DEFAULT_SUPERSEDED_PENALTY=1.0`), measured directly against the live 8-doc/36-chunk corpus via `run_eval(session, cases, reranker_model=DEFAULT_RERANKER_MODEL)`:

| Case | Task 6 (reranking alone) | Task 7 (+ status adjustment) |
|---|---|---|
| "How often must Kestrel employees rotate their VPN password..." | margin +3, correct | margin **+8**, correct |
| "How do I reset my Kestrel VPN password today?" | margin +1, correct | margin **+6**, correct |
| "What VPN client software should I currently install..." | margin **-1, FLIPPED** | margin **+8, fixed** |

All three cases now report `distractor_beats_best_relevant=False`, each with a wide (6-8 rank) positive margin, not just a narrow correct order -- the full-range penalty guarantee holds in practice, not just in theory. `apps/api/tests/test_eval_retrieval.py::test_reranked_eval_path_runs_end_to_end_against_real_corpus_and_reranker`'s distractor assertion is tightened from `<= 1` (Task 6's "known ceiling") to `== 0` (Task 7's zero-tolerance guarantee) -- a future change that reintroduces even one flip now fails CI.

**Net assessment**: this closes Task 6's flagged regression with a mechanism that is correct-by-construction (not curve-fit to the one measured case), verified against the real corpus, and enforced going forward by a CI-blocking test. Deprioritization (not filtering) is deliberate -- a superseded chunk can still survive into the final context if no non-superseded chunk covers the same point (e.g. "what was the OLD policy"), matching this whole phase's established "erring toward under-hiding, not silently deleting real content" philosophy.
